card-auth-saga: card authorization as a Temporal saga

Oct 27, 2026 · 6 min read

TL;DR
  • A card issuer's backend in Go: one Temporal workflow per authorization, one per card's statement cycle, a nightly auditor, and a double-entry MySQL ledger where every posting sums to zero.
  • Temporal took the orchestration off my hands but not the ledger. With the row lock removed, MySQL accepted 20 holds worth 200 against a limit of 100, in 3 of 3 runs. With it, exactly 10 get through.
  • Under load at 50-way concurrency, 400 simultaneous auths on one card approve exactly 5 (the velocity limit), and the audit afterwards is clean.

Card authorization looks like one request, but it's a long-running process with money at every step. The issuer places a hold, waits up to a week for the merchant to capture, settles the captured amount, releases the rest, accrues rewards, and keeps taking refunds for another month. Every step has to survive retries, crashes and duplicate messages without posting money twice or losing it.

At Capital One I built resiliency machinery for card authorizations the hard way: distributed leases on DynamoDB, and retry and failover logic we wrote and operated ourselves. This project asks a narrower question: how much of that does a durable-execution engine take off your hands, and what still has to be designed carefully? The answer turned out to be "the orchestration, but not the ledger".

Shape

  • One workflow per authorization (AuthorizeWorkflow), which lives as long as the transaction. An authorize update, sent with Update-with-Start, returns approve or decline as soon as the hold is placed, with a reason: over the limit, velocity, frozen, closed, or unknown card. The hold takes increments and partial captures until a final capture, a reversal, or a 7-day timer closes it. After capture it takes refunds and disputes.
  • One workflow per card for statements (StatementWorkflow). Each run is one cycle: daily balance samples, a late fee on the due day, and interest on the average daily balance at close. Then it continues as new, so history never grows past a cycle.
  • A nightly auditor (AuditWorkflow on a Temporal Schedule) checks the ledger's invariants and looks for stuck or failed workflows. /healthz reports any findings, so the Operate stage's prober turns them into incidents.
  • Compensations, not mutations. Reversals, failed captures, refunds, provisional credits and rebills each post new balancing entries. History is never edited.
  • Rewards in points, funded by the brand partner's account, so points balance the same way money does.

What Temporal did not solve

Check-then-act on the limit. The first milestone checked the card's limit in one activity and placed the hold in the next. Temporal ran both reliably, which didn't help: two concurrent authorizations on one card could both pass the check. The fix belongs in the ledger. PostWithin locks the card's account rows (SELECT … FOR UPDATE, in sorted order) so the check and the hold commit in one transaction. Removing the lock as an experiment let MySQL accept 20 holds worth 200 against a limit of 100, in 3 of 3 runs. With it, exactly 10 get through.

A deadlock hiding in "create if missing". INSERT IGNORE on an account row that already exists takes a shared lock, and FOR UPDATE then needs to upgrade it. Two holds on one card would each hold the shared lock and wait on the other. Account rows are now created before the transaction starts.

Rounding. Clawing back each refund's own rounded points leaves stray points after a full refund ($2.00 refunded as $1.50 + $0.50 claws back 1 + 0 of 2 points). The clawback is instead points(remaining before) − points(remaining after), at the rate fixed at settlement, so a full refund always lands on exactly zero.

Check-then-act again, inside the workflow. Updates run as concurrent handlers. Workflow code is single-threaded, but every activity is a yield point, so a second capture could pass its validator while the first was still posting. Each step now claims its share before its first activity: a capture or release marks the hold busy, and a refund reserves its amount and ID. The test environment can't produce these races, since activities there take no time, so a drill with a slow ledger forces them.

Evidence

Failure drills

The drills run the real worker against a real Temporal dev server, on the in-memory ledger or on MySQL. Each checks exact balances afterwards, then replays the recorded history. A selection:

Every safeguard was also removed on purpose to confirm a test notices. Removing idempotency on posting keys makes the timeout drill post the capture twice (60,000 vs 30,000). Removing a GetVersion gate makes 5 of the 6 recordings from before that change fail to replay. Recorded histories live in testdata/ and replay on every commit, so a nondeterministic workflow change fails CI with Temporal's TMPRL1100.

Under load

CAS_LOAD=1 go test -run TestLoad drives the real worker against a Temporal dev server and MySQL 8.4 at 50-way concurrency, capturing each approved auth. Typical numbers from three runs on an Apple M5 Pro:

ScenarioThroughputDecision p50 / p99Approved
Spread: 400 auths over 100 cards~140 auths/s~130 / ~570–770 msall 400
Hot card: 400 at once on one card~300–470 auths/s~85 / ~240–340 msexactly 5
Limit contention: 100 over 20 cards, limits cover 3 each~200 auths/s~110 / ~320 msexactly 60

The counts are the point: the velocity check admits exactly 5 of 400 simultaneous attempts on one card, the row locks admit exactly the 3 that each limit covers, and the auditor finds nothing afterwards. Running PlaceHold as a local activity cut median decision latency by 30–45%, and raising the idle connection pool from database/sql's default of 2 to 64 took hot-card throughput from ~350 to ~470 auths/s.

The same test against a throwaway copy of the Fly.io stack kept every count exact and the audit clean, but started at 2–3 auths/s. Three fixes, each found from the worker's own timers, got it to 18–31 auths/s with medians of 0.7–1.2s:

Production runs on shared CPUs, so it has the first two fixes but not the third. Dedicated CPUs cost about $90/month for the three machines against about $10/month now; that's the change to make before real traffic.

Run it

brew install temporal          # one-time: Temporal CLI
temporal server start-dev      # local server + web UI on http://localhost:8233
go test -short ./...           # unit + workflow tests (no server needed)

docker run -d --name cas-mysql -e MYSQL_ROOT_PASSWORD=cas -e MYSQL_DATABASE=cas -p 3307:3306 mysql:8.4
export CAS_MYSQL_DSN='root:cas@tcp(127.0.0.1:3307)/cas'
go test ./...                  # adds the ledger contract, migrations and drills against MySQL

go run .                       # worker on task queue card-auth
go run . authorize auth-9 card-1 shell 1000   # approved, declined (Reason), or Timeout and reversed
go run . audit                 # "audit: clean", or the findings and exit 1
